Lesson 1

LLM basics: tokens, context window, temperature

What an LLM actually does

An LLM does one thing over and over: it predicts the next piece of text. You give it some text, it works out a probability for every possible next piece, picks one, adds it, and repeats until it's finished. Every answer is built one piece at a time.

Given "The BGP session is", the next-piece probabilities might be:

Next pieceProbability
" down"45%
" up"30%
" established"15%
" flapping"5%
everything else5%

Those pieces are called tokens.

1. Tokens

A token is the unit of text a model reads and writes, usually a word or part of a word. Each model has a fixed vocabulary of about 30,000–200,000 tokens, and all text is split into pieces from it:

  • "Cisco routers are reliable" → Cisco · routers · are · reliable (4 tokens)
  • "IOS-XR" → IOS · - · XR (uncommon words get split)
  • "10.24.156.3" → about 7 tokens. IP addresses, logs, code and JSON use more tokens per word.

Rules of thumb (English): 1 token ≈ 4 characters ≈ ¾ of a word. 1 word ≈ 1.33 tokens. Tokens are smaller than words, so you always get more tokens than words: 3,000 words ≈ 4,000 tokens; 600 words ≈ 800 tokens.

Tokens matter because cost (APIs charge per input and output token), limits (the context window) and speed (one token written at a time) are all measured in them.

2. Context window

The context window is the maximum number of tokens the model can handle in one request. It's one box that has to hold everything: the instructions, the chat history, retrieved documents, tool results, and the answer the model writes. Common sizes today are about 128K–200K tokens; some reach about 1M.

Why the answer counts

The answer is written inside the same API call, one token at a time, and each new token is added to the text the model is reading. To choose the next token, the model needs the whole text so far: your input plus everything it has already written.

StepWhat the model is looking atWhat it does
1Your input (32,000 tokens)Writes token 1: "To"
2Input + "To" (32,001)Writes token 2: "upgrade"
3Input + "To upgrade" (32,002)Writes token 3: "IOS-XR"

When you call the API you also send max_tokens, the longest answer you'll allow. So the API can check before doing any work: input tokens + max_tokens ≤ context window? If not, most APIs return an error ("prompt is too long"); some cut the answer off when the box fills.

Worked example

Goes in the windowTokens
Instructions2,000
30 chunks × 1,00030,000
Used before the answer starts32,000
Window size32,000 → no room for the answer

Fix: re-rank and send only the top 5 chunks: 2,000 + 5,000 = 7,000 used, 25,000 left. Cheaper, faster and usually more accurate.

How to check every time: (1) add up the input: instructions + chunks × chunk size + question; (2) add max_tokens; (3) compare with the window.

Why there's a limit, and why bigger isn't better

  • Each token is compared with every other token, so double the length roughly quadruples the work.
  • A very full context costs more, is slower, and can be less accurate: models tend to miss details buried in the middle.
  • Context window management = deciding what goes in the box: only the relevant pieces, in a compact form. SVS Pulse does this: pre-structured records instead of raw data, 50K → 3K tokens per report.

3. Temperature

Temperature controls how random the model is when picking the next token.

TemperatureBehaviourBGP example
0Always the top choiceAlways " down". Nearly the same output every time.
1Uses the real probabilities" down" ~45% of the time, " up" ~30%…
1.5+Flattens the oddsMore varied, more mistakes
  • 0–0.3: classification, extraction, code, answers from your own data (SVS Pulse reports).
  • 0.7–1.0: brainstorming and writing.
  • Trap: low temperature does not stop hallucination. It makes the model consistent, not correct. Grounding reduces hallucination.
  • Top-p: pick only from the smallest set of tokens whose probabilities add up to p (e.g. 0.9).

Token: "The unit an LLM reads and writes, about 4 characters in English. Cost, speed and limits are measured in tokens."

Context window: "The maximum tokens per request, counting prompt, history, retrieved data and the output. I keep context small and relevant, as in SVS Pulse, 50K down to 3K."

Temperature: "Controls randomness in picking the next token. Low for factual work. It doesn't reduce hallucination; grounding does."

Check yourself

A 3,000-word document is roughly how many tokens?

About 4,000 (3,000 × 1.33). Dividing by 4 is the rule for characters, not words.

A 2,000-token prompt plus 30 chunks of 1,000 tokens, on a 32K model. What goes wrong?

The input is exactly 32,000, the whole window, so there's zero room for the answer. Re-rank and keep the top 5 chunks.

16K window; 1K instructions; 10 chunks of 1.5K; max_tokens 1K. Does it fit?

No. 1,000 + 15,000 + 1,000 = 17,000, which is 1,000 over. Send the top 6 chunks: 11,000 total. Chunk size and max_tokens are different numbers: max_tokens only limits the answer.

Which temperature for the SVS Pulse report assistant, and why?

0. Reports must be factual and the same every time. Temperature makes it consistent; grounding in records keeps it accurate.

Lesson 2

Embeddings & vector search

The problem

An engineer searches "BGP neighbor down". The answer document says "peer session dropped on the router." They share no words, so keyword search misses it. We need search by meaning.

1. What an embedding is

An embedding is a list of numbers that represents the meaning of a piece of text, produced by an embedding model (a separate, smaller model from the chat LLM). Similar meanings get similar numbers. "Vector" just means a list of numbers.

TextToy embedding [networking, failure, food]
Question: "BGP neighbor down"[0.90, 0.80, 0.00]
A: "Peer session dropped on router"[0.85, 0.90, 0.05]
B: "OSPF configuration guide"[0.90, 0.10, 0.00]
C: "Best biryani in Bangalore"[0.00, 0.10, 0.95]

Real embeddings have hundreds to a few thousand numbers (384, 768, 1,536…). The model learns what they mean.

2. Cosine similarity

One score for "how similar": 1.0 = same meaning, 0 = unrelated. (Multiply the lists number by number, add up, divide by both lengths.)

DocumentSimilarity to the question
A: "Peer session dropped on router"0.99, best match with no shared words
B: "OSPF configuration guide"0.82, networking but not a failure
C: "Best biryani in Bangalore"0.07, unrelated

3. Vector search end to end

Indexing (once): split documents into chunks → embed each chunk → store text + vector in a vector database.
Searching (every question): embed the question with the same model → find the closest stored vectors → return the top-k chunks.

Same model, always: each model builds its own number space, so vectors from two models are like coordinates on two different maps.

4. pgvector

A PostgreSQL extension that stores vectors next to normal data. I used it in EcoVisionaries.

CREATE EXTENSION vector;
CREATE TABLE chunks (
  id        serial PRIMARY KEY,
  text      text,
  embedding vector(1536)
);
-- 5 chunks closest in meaning to the question
SELECT text FROM chunks
ORDER BY embedding <=> '[0.12, -0.03, ...]'   -- <=> = cosine distance
LIMIT 5;
  • Distance = 1 − similarity, so the smallest distance is the best match (ascending sort).
  • ANN (approximate nearest neighbour): indexes like HNSW and IVFFlat find almost the closest vectors much faster than comparing against all of them.
  • Other vector databases: Pinecone, Weaviate, Milvus. Same idea.

5. Where embeddings fail

They're weak on exact identifiers: bug IDs (CSCwe12345), IPs, serial numbers, error codes. CSCwe12345 and CSCwe12346 get nearly identical vectors. The fix is hybrid search: keyword search plus vector search, merged. And high similarity means "similar meaning," not "correct."

Search typeMatches"router CPU spike" picks
Keywordsame words"Router configuration backup steps" ❌ (shares "router")
Vectorsame meaning"High processor utilization on ASR 9000" ✅
Hybridboth"High processor utilization on ASR 9000" ✅

"An embedding is a list of numbers, produced by an embedding model, that represents a text's meaning. For vector search I embed and store chunks once, then embed the question with the same model and return the closest chunks by cosine similarity. I used pgvector in Postgres. Embeddings are weak on exact IDs, so I'd add keyword search: hybrid search."

Check yourself

"Switch memory leak": which wins with keyword search, and which with vector search? A: "Switch port naming conventions"; B: "Gradual RAM growth on Catalyst 9300 until it crashes"

Keyword: A, because it shares "switch." Vector: B, because RAM growth until crash means memory leak, and a Catalyst 9300 is a switch.

A search for bug "CSCwe12345" returns the wrong bug. Why, and what would you add?

An ID has no meaning for an embedding to capture, so similar IDs get almost identical vectors. Add keyword search, i.e. hybrid search.

Why embed questions and documents with the same model?

Each model has its own number space; vectors from different models can't be compared, even for the same sentence.

Lesson 3

RAG end to end

The problem RAG solves

  1. The LLM doesn't know your private data (CXTM, recordings, internal docs).
  2. Its knowledge stops at a cutoff date.
  3. You can't paste everything into the context window.

RAG (Retrieval-Augmented Generation): first find the few relevant pieces of your data, then give only those to the LLM and have it answer from them. It's an open-book exam. Retrieval = find the pages; augmented = add them to the prompt; generation = the LLM answers.

Phase 1: Ingestion (ahead of time)

StepWhat happensSVS One example
1. LoadPull in source dataRecordings → transcripts, plus 430+ resources
2. CleanRemove junkStrip filler words, noise, duplicates
3. ChunkSplit into small pieces8.1K transcript chunks
4. EmbedVector per chunkEmbedding model
5. StoreText + vector + metadataSession, date, speaker, who may see it

Phase 2: Query (every question)

  1. Embed the question with the same model.
  2. Retrieve the top ~20 closest chunks.
  3. Filter out chunks this user may not see (metadata).
  4. Re-rank and keep the best ~5.
  5. Build the prompt: instructions + chunks + question.
  6. Generate the answer, with sources.
SYSTEM:
You are a support assistant for the SVS team.
Answer ONLY using the context below.
If the answer is not in the context, say "I don't know."
Cite the source ID for every fact, like [S2].

CONTEXT:
[S1] (Session: CXTM onboarding, 12 Mar) "To create a test case in CXTM, open..."
[S2] (Session: Automation tips, 4 Apr) "Robot suites are linked to CXTM by..."

QUESTION:
How do I link a Robot test suite to CXTM?

Chunking

Too small (~50 tokens)Too big (~3,000 tokens)
Loses context; needs many chunksOne vector covers many topics, so matching blurs; wastes the context window
  • Start around 300–800 tokens, then test.
  • Overlap ~10–20% so ideas across a boundary aren't lost.
  • Split at headings, paragraphs or speaker turns, never mid-sentence.

Evaluating RAG

  1. Retrieval: did the right chunk come back? Measure recall@k on test questions.
  2. Generation: is the answer correct and faithful (based only on the chunks)?

Test them separately: a bad answer can come from either, and the fixes differ.

RAG vs fine-tuning

RAGFine-tuning
TeachesFacts (by lookup)Behaviour, style, format
UpdatingRe-indexRetrain
SourcesYesNo
CostLowHigher

Use RAG for knowledge and fine-tuning for behaviour. Retrieval doesn't have to be vector search: a database query or API call counts too.

"RAG retrieves the most relevant pieces of our own data and gives them to the LLM as context, so it answers from current, private data with sources. In SVS One I chunked and embedded 8.1K transcript chunks; at query time I retrieve, filter by access, re-rank to the top few, and answer only from those, with citations. When it fails, I check retrieval and generation separately."

Check yourself

Why use RAG instead of asking the LLM directly?

The LLM doesn't know our private or recent data, and we can't paste everything in. RAG fetches just the relevant pieces so it answers from them, with sources.

The assistant says "I don't know," but the right document is in the database. Which stage failed? Two fixes?

Retrieval. Fixes: better chunking, hybrid search, query rewriting, HyDE.

Chunks are 3,000 tokens each. Two problems?

Each vector mixes many topics, so matching gets blurry; and fewer chunks fit in the context window, wasting tokens.

A user without access asks about Project X. Where do you stop the leak, and why isn't a prompt instruction enough?

At retrieval: filter chunks by the user's permissions so restricted chunks never reach the prompt. A prompt instruction fails because the model doesn't know who's authorised, users can trick it, and once the chunk is in the prompt it has already leaked.

Lesson 3b

RAG failures in detail

Running example: an SVS team assistant answering from team docs and session transcripts.

What failsSymptomFixes
Retrieval missesRight doc exists but wasn't retrievedChunking, hybrid search, query rewriting, HyDE
Irrelevant chunksLoosely related chunks; answer driftsRe-ranking, metadata filters, similarity threshold
Not groundedGood chunks, but invented factsStrict instructions, temperature 0, citations, evaluation
Context overflowRequest fails or answer cut offSmaller top-k, smaller chunks, trim history, compress tool output
Stale answersOld content after docs changeRe-index on schedule or on change
Access leakUser sees restricted contentFilter by permissions at retrieval

1. Retrieval misses

Looks like: "How do I link a Robot suite to CXTM?" The answer chunk says "…to attach your automation to a test case, use the cxtm-cli upload command…" but it isn't in the top 5.

Why: the answer was split across chunks or buried in a huge one; different wording; exact terms embeddings handle badly; vague questions.

Spot it: log retrieved chunks. If the right one isn't in the list, it's retrieval, not the LLM.

  • Better chunking: natural boundaries plus overlap; one idea per chunk.
  • Hybrid search: keyword catches exact terms; vector catches different wording.
  • Query rewriting: an LLM turns "it's broken after upgrade" into "BGP sessions not recovering after NX-OS upgrade," or searches several rewrites.
  • HyDE: generate a fake answer first and search with it, since answers resemble answer chunks more than questions do.

2. Irrelevant chunks

Looks like: "Escalation process for a P1 on the Verizon project?" returns escalation for a different project, P1 definitions and onboarding. The model blends them into a confident wrong answer.

Why: vector search always returns top-k, never "no match"; similar topics for different projects look alike; it knows nothing about project or date.

  • Re-ranking: retrieve ~20, have a careful model score each chunk with the question, keep the best 5.
  • Metadata filters: e.g. only project = Verizon or recent dates.
  • Similarity threshold: drop weak matches; if none pass, say "I don't know."

3. Not grounded

Looks like: the chunk says "Upgrade window is Saturday 2–6 AM." The answer adds "notify the NOC 48 hours before," which isn't in any chunk.

Why: models fill gaps with likely-sounding text; instructions didn't forbid it; higher temperature adds randomness.

  • Strict instructions: "Answer ONLY from the context; otherwise say I don't know."
  • Temperature 0: consistency helper, not the main fix.
  • Citations: keep the model close to sources and let you auto-flag uncited sentences.
  • Evaluate faithfulness on a test set so you know if changes help.

4. Context overflow

Why: input + max_tokens exceeds the window; history grows; agents pile up tool output. Even below the limit, full contexts cost more and lose accuracy.

  • Retrieve 20, re-rank, send 3–5.
  • Smaller chunks; trim or summarise history; extract only relevant log lines.
  • Pre-structure data: SVS Pulse, 50K → 3K.

5. Stale answers

Why: the vector database is a copy of the docs at ingestion time; edits and deletions don't flow through by themselves.

  • Nightly re-index of changed docs, or re-index on change (store a document ID per chunk).
  • Store and show last_updated; prefer newer chunks on conflict.

6. Access leak

Why: the store holds everyone's chunks and search doesn't know who's asking. A prompt instruction can't fix it: the model doesn't know who's authorised, prompt injection can override it, and once a chunk is in the prompt it has leaked.

  • Store permissions as metadata (project, allowed_groups).
  • Filter in the search itself, so restricted chunks never come back.
  • Take the user's groups from SSO / LDAP, never from what they type; keep permissions in sync.

"When a RAG answer is wrong, I first check retrieval: was the right chunk retrieved? If not, chunking, hybrid search or query rewriting. If the chunks are right but the answer adds facts, it's grounding: tighter instructions, citations, faithfulness evals. Access control always happens at retrieval, never in the prompt."

Lesson 4

Edge AI & small models

Why small models at the edge

Factories and plants often have little or no internet, strict privacy rules, and need fast responses, so the model runs on the device: a switch, gateway or industrial PC. The job is a trade-off between quality, memory, compute and latency.

Quantization, from zero

A model is a huge list of numbers (weights). "1B model" = 1 billion numbers, and all of them must fit in RAM to run.

Every number takes space in bits (8 bits = 1 byte). 16-bit allows ~65,000 values per number (precise, 2 bytes). 4-bit allows only 16 values (rough, half a byte).

Quantization = rounding the numbers to fewer levels, like rounding ₹523 to ₹520. With weights between −1 and 1, 4 bits gives 16 evenly spaced allowed values: −1.0, −0.87, −0.73 … 0.47, 0.60 … 1.0. The weight 0.52 becomes 0.47 and is stored as "level 11" in 4 bits; at run time level 11 turns back into 0.47. That small error is the accuracy loss.

Stored asPer number1B model3B model
16-bit2 bytes~2 GB~6 GB
8-bit1 byte~1 GB~3 GB
4-bit0.5 bytes~0.5–0.7 GB~1.5–2 GB

In one line: 4-bit makes a model about 4× smaller and faster with slightly lower accuracy, like a smaller, slightly blurrier JPEG. Post-training quantization is quick; quantization-aware training keeps more quality. Formats: GGUF (llama.cpp), INT8 TF Lite.

Fine-tuning, LoRA, PEFT, QLoRA

  • Full fine-tuning updates every weight: expensive, makes a full new copy.
  • LoRA freezes the base model and trains two small matrices (A × B) added to chosen layers. Only ~0.1–1% of parameters train, and the result is a small adapter file you can merge or swap.
  • QLoRA = LoRA on a 4-bit base, so it fits on one free GPU.
  • PEFT = parameter-efficient fine-tuning, the umbrella term and the Hugging Face library.

Distillation

A big teacher model's outputs train a small student. Example: a frontier LLM labels 2,000 syslog lines; a 1B model learns from those labels and gets near-teacher quality at a fraction of the size.

On-device inference

  • llama.cpp: runs GGUF models in C/C++ on CPU and ARM, no GPU needed.
  • TF Lite: runs small ML and vision models on edge chips.
  • Always measure RAM, tokens/second, p95 latency and accuracy before and after quantization.

Check yourself

How much memory do a 3B model's weights need at 4-bit?

3B × 0.5 bytes = 1.5 GB, plus overhead: about 1.5–2 GB (vs ~6 GB at 16-bit).

What does LoRA actually train?

Small low-rank matrices added to frozen layers. The base model stays frozen.

A big LLM labels data and a 1B model trains on the labels. What is this called?

Distillation (teacher → student).

After 4-bit quantization, F1 drops from 0.91 to 0.82. First step?

Try higher precision (5- or 8-bit) and compare size, latency and F1; pick the smallest that meets the target. Next option: quantization-aware training.

Kubernetes, explained with SVS Pulse

SVS Pulse already solves the problems Kubernetes solves, by hand, on one Linux VM.

On the SVS Pulse VMIn Kubernetes
FastAPI processPod: one or more containers running together
systemd restarts it on crashDeployment keeps N copies running
Nginx forwards trafficService (stable address) + Ingress (outside HTTP in)
.env with DB URL and keysConfigMap (settings) + Secret (keys)
PostgreSQL on the VM diskStatefulSet + PersistentVolumeClaim
Staging vs productionNamespaces or separate clusters
Deploy scriptkubectl apply with a rolling update

One VMA cluster of nodes

The big idea: declarative desired state. You declare "3 copies of this app," and controllers keep comparing what is running with what should be, fixing any difference. Delete a pod and it comes back.

Architecture: the control plane has the API server (everything talks to it), etcd (the database), the scheduler (picks a node for each pod) and controllers (fix differences). Each node runs the kubelet (starts containers) and kube-proxy (networking).

Labs (in order)

Where: Killercoda (free, in the browser), or kind / minikube locally. On a work laptop use Podman: minikube start --driver=podman.

Lab 1: first cluster (~45 min)

kind create cluster --name fde          # or: minikube start
kubectl get nodes
kubectl create deployment hello --image=nginx --replicas=2
kubectl get pods -o wide
kubectl delete pod <pod-name>          # then: kubectl get pods -w
kubectl expose deployment hello --port=80
kubectl port-forward svc/hello 8080:80 # open localhost:8080
kubectl scale deployment hello --replicas=4
kubectl set image deployment/hello nginx=nginx:1.27   # rolling update
kubectl rollout undo deployment/hello                 # roll back
kubectl describe pod <pod-name>; kubectl logs <pod-name>
  1. Your own app: containerize a small FastAPI service; write the Deployment and Service YAML by hand.
  2. Config & health: ConfigMap, a Secret for an LLM key, probes, CPU/memory limits.
  3. Data: PostgreSQL via Helm; delete the pod and confirm the data survives.
  4. Traffic & scaling: Ingress, then a HorizontalPodAutoscaler; load-test until it scales.
  5. Capstone: see Kubernetes capstone.
  6. Break-it drills: CrashLoopBackOff, ImagePullBackOff, Pending, OOMKilled, wrong Service selector.

Check yourself

You delete one pod of a Deployment with replicas=3. What happens?

A controller sees 2 running instead of 3 and creates a replacement.

Which object gives a set of pods one stable internal address?

A Service. An Ingress then routes outside HTTP traffic to Services.

Where does an LLM API key go?

A Secret. Never a ConfigMap, never baked into the image.

Pod in CrashLoopBackOff. First command?

kubectl logs <pod> --previous to see why the last run died; then kubectl describe pod.

Which component decides which node a new pod runs on?

The scheduler.

A software engineer who works directly with a customer and builds whatever makes the company's product work inside that customer's business. Part engineer (production code), part consultant (find the real problem), part product scout (feed back what customers keep needing).

A typical engagement

  1. Discovery: learn workflows, data, systems, pain points. "What does success look like in 3 months?"
  2. Scoping: turn a vague wish into a concrete, buildable plan.
  3. Prototype on real data.
  4. Production: security review, access control, monitoring, error handling, integration (SSO, databases, ticketing).
  5. Measure and iterate.
  6. Feed back to the product team.

Skills

  • Technical breadth: Python/TypeScript, APIs and auth, quick UIs, SQL and ETL, Docker, a cloud, CI/CD, debugging unfamiliar systems.
  • AI-focused FDE: LLM APIs and tool calling, RAG, agents, evals, guardrails, privacy, hallucination handling.
  • People: good questions, explaining trade-offs to non-technical people, managing scope, deciding with incomplete information.

Agent observability concepts (for AI-agent platform teams)

  • Agent evaluation: scoring what an agent did: action completion, tool selection, hallucination, RAG adherence.
  • Evals become guardrails: an eval that scores reliably in testing is promoted to a runtime check that blocks a bad action before the tool fires.
  • Cheap always-on evaluation: small evaluator models score every interaction; a frontier LLM as judge is too costly and slow at scale.
  • Token and cost tracking by request, model, agent and workflow.
  • OpenTelemetry: traces, spans, and the collector that ships them.

What FDE interviews test

  • Practical coding (parse this data, build this small API).
  • Case rounds: "A hospital wants AI to summarise patient records. Walk me through it."
  • Customer scenarios: "The demo is wrong and their VP is angry. What do you do?"
  • Behavioural: ambiguity, ownership, difficult stakeholders.

My honest gap: no direct customer work. My closest story is SVS Pulse with internal users: found their problem (30–40 min report prep), built the fix, got a PRD approved, demoed it at a showcase booth.

Edge NetOps agent

Closes the small-model gap and builds on my network-agent work.

  1. Data: 1–2K syslog lines from a lab or synthetic, labelled by a big LLM (link flap, BGP down, high CPU, auth failure, normal). That's the distillation story. Clean the text first. Never use customer logs on a personal machine or Colab.
  2. Baseline: TF-IDF + logistic regression; record F1.
  3. Fine-tune a ~1B open model with LoRA (Hugging Face transformers + peft, free Colab).
  4. Quantize: merge the adapter, convert to GGUF, 4-bit, run with llama.cpp on a laptop CPU.
  5. Agent: wrap the classifier as an MCP tool; a LangGraph agent classifies the log, then runs show commands through NetAuto MCP.
  6. README: one table: model | size | RAM | tokens/s | F1. That table is the interview story.

Kubernetes capstone

  1. Instrument a small agent app with OpenTelemetry.

AI concepts

Explain LoRA.

Freeze the base model; train two small low-rank matrices added to selected layers; ~0.1–1% of parameters; a small adapter file.

How much RAM does a 3B model need at 4-bit?

~1.5–2 GB (0.5 bytes per weight plus overhead).

How would you detect anomalies in network telemetry?

Learn a baseline per metric; flag deviations with z-score or EWMA; isolation forest or autoencoders for multi-metric patterns; then use an LLM to explain the likely cause from logs and context.

Design an agent that troubleshoots an industrial switch with no cloud access.

Quantized small model running locally (llama.cpp); tools for read-only show commands; a local log classifier; RAG over a local runbook index; human approval before any config change; a budget for memory and latency; logs of every action.

Networking

TCP vs UDP, and the 3-way handshake.

TCP: connection-based, ordered, reliable (SYN → SYN-ACK → ACK). UDP: connectionless, no delivery guarantee, lower latency (DNS, streaming, syslog).

What does a port flap look like, and how would you investigate?

Repeated link up/down syslog messages on an interface. Check interface counters and errors, optics levels, cabling, the far end, and spanning tree or LACP events.

Name three industrial protocols.

Modbus, PROFINET, OPC UA. Know one line on each.
